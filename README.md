# QTranslator

跨平台（Windows / Linux）截图翻译工具。截取屏幕区域，识别其中文字，翻译后覆盖回原图。

模仿微信截图翻译的效果：**擦掉原文，把译文按原排版贴回去**。

## 当前进度

| 阶段 | 内容 | 状态 |
|---|---|---|
| 一 | 截图 → 选区 → OCR → 预览 | ✅ |
| 二 | 块聚类 → 翻译 → 擦除 → 回填排版 | ✅ |
| 三 | 列分割 + 字体启发式匹配 | ✅ |
| 四 | 真实翻译接入（DeepSeek / 智谱）+ 关闭推理 | ✅ |
| 五 | 手动纠正块、本地 LLM | 待做 |
| 六 | Windows 签名、Linux AppImage + Flatpak | 待做 |

## 工作流

```
热键 (默认 Ctrl+Alt+Q)
  → 抓光标所在显示器全屏（物理像素）
  → 全屏暗化选区窗，用户拖选矩形
  → 反算回物理像素坐标裁剪
  → OCR 识别，得到 [{quad, text, score}]（后台线程）
  → 版面分析：先横切成带（页头/正文），再在带内竖切成列
  → 在每个列内聚类成段落块 + 提取样式（字号/颜色/背景/粗体/对齐）
  → 整屏批翻（一次送出所有块，带上下文）
  → 按背景复杂度分档擦除原文
  → 字体启发式匹配（serif/sans + 字重）选出最接近的字体
  → shrink-to-fit 回填译文（CJK 禁则断行 / 拉丁按词断行）
  → 预览窗：原文 ⇄ 译文 切换，可保存
```

## 翻译后端

已接入并验证两家，接口都是 OpenAI 兼容的。**默认 DeepSeek + 关闭推理**：
实测 1.0s/屏，而智谱 glm-4-flash 需 6-10s。

```bash
export QTRANSLATOR_API_KEY=xxx
export QTRANSLATOR_BASE_URL=https://api.deepseek.com
export QTRANSLATOR_MODEL=deepseek-flash
```

内置厂商预设（`config.py` 的 `PROVIDER_PRESETS`）：`deepseek`、`deepseek-pro`、
`glm`、`glm-flash`、`siliconflow`、`dashscope`、`openai`、`ollama`。

配置位置：Windows `%APPDATA%/QTranslator/config.json`，
Linux `~/.config/qtranslator/config.json`。

**未配置 key 时自动退回 MockTranslator**，产出长度和字宽接近真实译文的占位
文本，让排版管线仍可验证。

### 关闭推理：最大的性能杠杆

推理模型会为每屏生成上千个 reasoning token，而翻译短文本完全不需要思考。
实测对比（4 个短句，`tools/probe_api.py`）：

| 参数 | 耗时 | reasoning_tokens | 质量 |
|---|---|---|---|
| DeepSeek 默认 | 6.2s | 1214 | 好，但把 "AI" 译成"人工智能" |
| **`reasoning_effort: none`** | **1.0s** | **0** | **更好**（保留 "AI" 缩写） |
| `thinking: {type: disabled}` | 1.0s | 0 | 同 none |
| `reasoning_effort: minimal` | 11.5s | 2180 | 比默认还慢一倍 |
| `effort: low` | 1.6s | 233 | 该字段语义与名字不符 |

**关键教训：各厂商字段名和语义都不统一，只能实测。** `minimal` 比默认更慢、
`effort` 和 `reasoning_effort` 是两个不同参数——这些靠猜都会踩坑。所以留了
`tools/probe_api.py` 专门做这件事：

```bash
python tools/probe_api.py https://api.deepseek.com <key> deepseek-flash
```

它列模型 + 逐个试参数组合 + 报告 reasoning token 与耗时。

配置项 `disable_reasoning`（默认 true）控制是否发 `reasoning_effort: none`。
若某厂商不认这个参数导致报错，设为 false 或 `QTRANSLATOR_DISABLE_REASONING=0`。

### 两个必须处理的 API 现实

1. **厂商在 HTTP 200 里返回业务错误。** 智谱过载时返回
   `{"error":{"code":"1305",...}}` 而状态码是 200。不检查 `error` 字段就会把
   错误当成功解析，然后在 JSON 解析处报一个莫名其妙的错。
2. **推理模型的 `content` 可能是空的。** 输出全被思考链占满时（`max_tokens`
   太小），`content` 为空而 `reasoning_content` 里有内容。代码会退回读
   reasoning，比直接失败好。

### 重试

智谱的 1305 过载很常见（实测 3 次里 2 次失败）。客户端做指数退避重试
（1.5s / 3s / 6s，共 3 次），并区分可重试（429、5xx、网络抖动）与不可重试
（认证失败等 4xx）。DeepSeek 实测未见此问题。

### 品牌名保护

模型会把品牌名按词源意译——实测 `ANTHROPIC` 被译成 `人类学`（"anthropology"）。

**只在 prompt 里解决**：规则明确要求 ALL CAPS / 混合大小写 / 含符号的 token
视为品牌名并原样保留，且直接举了 `Anthropic ≠ 人类学` 的反例。

曾加过一层正则兜底（找出原文全大写 token、译文里没有就补回），**已移除**。
理由：这是措辞问题，正确做法是把 prompt 写清楚，而不是在代码里猜哪段文本
是品牌名。兜底本身还会引入新错误——它靠字面匹配判断，模型若输出
`Anthropic` 而非 `ANTHROPIC` 就会误判，然后往正确译文里塞多余 token。

实测 prompt 修复后连续 3 次运行均正确保留 `ANTHROPIC` 与 `Anthropic`。

## 擦除策略

按背景复杂度自动选档，不是一律上模型：

| 档 | 触发条件 | 实现 |
|---|---|---|
| **fill** | 背景方差 < 90（纯色/均匀） | 用采样的背景色直接填 |
| **telea** | 有轻微纹理/渐变，无 MI-GAN 模型 | OpenCV `cv2.inpaint` |
| **migan** | 有纹理且配了模型 | MI-GAN ONNX（需自备模型文件） |

UI 截图以平坦背景为主，所以绝大多数块走 fill——微秒级且比任何 inpainting 都干净，
因为纯色背景的"正确"结果就是那个颜色，插值只会引入涂抹感。

MI-GAN 模型不在仓库里（体积原因）。要启用就下载后设 `QTRANSLATOR_MIGAN_MODEL`。

## 版面分析：先横切带，再竖切列

顺序不能反，这是实测踩出来的：

**只做全局竖切会失败。** 页面常常同时有「通栏页头」和「两栏正文」。全局垂直
投影下页头横跨整个宽度，找不到贯穿所有行的空白竖带，正文两栏切不开；若放宽
度量，页面被从中间切开、页头被拦腰截断。两种错法都在实测样本上复现过。

**横切用行间距**（阈值 1.6 倍行高）。页头与正文之间的间隙（约 150px）远大于
段内行距（3-12px），判据很稳。

**竖切用空白竖带宽度**，阈值取 `min(1.2 × 行高, 4% × 文字总宽度)`。取较小值
是因为实测样本的两栏间隙 44px 与"1.5 × 行高"的阈值 45px 只差 1px——任何 OCR
抖动都会让切分失败。加上"文字总宽度百分比"这个不依赖行高的判据后稳健得多。

**块排序的 y 要量化。** 同一行带内并排的多个块（如导航栏各项）y 相差仅 1-3px，
直接比 y 会按 OCR 抖动顺序排列而不是左到右。量化步长取块高的一半。

## 字体启发式匹配

不引入模型，用像素统计判断三个特征，再从系统字体里挑最接近的：

- **衬线/无衬线**：比较字形上下边缘带与中部的前景像素占比。有衬线的字体在
  边缘有横向突起，占比相对更高。
- **字重档位**：笔画宽度 / 行高，分为 thin/regular/medium/bold/black。
  **单行块只区分"常规/粗"两档**——实测同为常规字重的相邻导航项，笔画估计会
  在 regular 和 medium 之间抖动，分太细会给同款文字选出不同字体。
- **等宽**：**刻意不检测。** 最初靠"行宽/字符数"的变异系数判断，结果在换行
  排版的段落上必然误判（折行后该比值天然稳定），而误判会选中 Consolas 这类
  **没有 CJK 字形**的字体，中文渲染成方块——比不匹配更糟。

匹配失败或置信度低于 0.5 时退回平台默认字体（选错比用默认更难看）。

## 排版复刻的关键决策

**shrink-to-fit，不做撑满。** 起始字号取原块中位行高，二分缩小直到译文在块宽内
断行后总高度 ≤ 块高。译文比原文短时宁可留白，也不放大字号——放大后的字号和
周围元素不协调，比留白更难看。

**断行分语种。** CJK 逐字断（带禁则：标点不起行、开括号不结尾），拉丁按词断
（超长单词硬断）。把中文按空格断行会得到一整行不换。

**mask 只覆盖笔画，不覆盖整个矩形。** 按整块矩形擦会把大标题的行间空白也抹掉，
重建后留下明显色块，比不擦更难看。

## 坐标系约定（重要）

整条管线**统一使用物理像素坐标**（`PixelRect`），因为多显示器混合缩放和
Linux HiDPI 下，屏幕逻辑坐标与物理像素不是 1:1。

- `PixelRect` —— 管线坐标系。截图裁剪、OCR、擦除、回填全部用它。
- `DisplayRect` —— 窗口显示坐标系（Qt 逻辑像素）。仅在窗口内部出现。

两者**只允许**通过 `coords.py` 的 `ViewTransform` 互转。缩放比取自 Qt 的
`QScreen.devicePixelRatio()`，不要用"物理宽度 ÷ 逻辑宽度"推算——后者在
多显示器混合缩放下会得到无意义的数。

## 界面

预览窗是**无系统标题栏**的，顶部一条自绘工具栏承担图标按钮、拖动窗口、
最小化/最大化/关闭三件事。这样 Windows 和 Linux 观感一致（系统标题栏在
两个平台上样式差别很大，跟深色工具栏拼在一起很割裂）。

**图标用 QPainterPath 矢量绘制**，不加载图片资源——避免打包时的资源路径问题，
且任意 DPI 都清晰。改图标只需改 `ui/icons.py` 里的路径数据。

### 操作

打开窗口时**不自动识别**——它就是个图片查看器：能缩放、能拖拽、能看清图内容。
识别和翻译由用户点按钮触发。

| 操作 | 方式 |
|---|---|
| 缩放图片 | 滚轮（以光标为锚点）/ 工具栏 `+` `-` |
| 平移图片 | 按住左键拖动 |
| 适应窗口 / 100% | 双击图片，或工具栏对应按钮，或 `Ctrl+0` / `Ctrl+1` |
| 拖动窗口 | 按住工具栏空白处拖动 |
| **缩放窗口** | **拖窗口四条边或四个角**（光标变为双箭头时拖动） |
| 最大化 | 双击工具栏空白处 |
| 切换原文/译文 | 工具栏 `‹` `›`，或 `Ctrl+←` / `Ctrl+→` |
| 识别 / 翻译 | `Ctrl+R` / `Ctrl+T` |
| **复制原图**（图片） | 工具栏「复制原图」按钮，或 `Ctrl+Shift+C` |
| 复制文本 / 保存图片 | `Ctrl+C` / `Ctrl+S` |
| 关闭 | `Esc` |

### 三个「复制」的区别

容易混淆，所以明确区分：

| 功能 | 给什么 | 何时可用 |
|---|---|---|
| **复制原图** | 原始截图（图片） | **随时**，不需要识别 |
| 复制译文图片 | 擦除+回填后的图 | 翻译完成后 |
| 复制文本 | 识别或译文的文字 | 识别完成后 |

「复制原图」不需要任何处理就能用——用户框选后常常只是想把这块图截走粘到
聊天窗口里，不该逼他先跑一遍 OCR。同理「保存图片」在没翻译时保存的是原图。

快捷键 `Ctrl+Shift+C` 是复制原图，`Ctrl+C` 是复制文本。**Shift 分支必须在
前面判断**，否则 `Ctrl+Shift+C` 会被 `Ctrl+C` 抢先匹配掉。

### 无边框窗口的边缘缩放

去掉系统装饰后（`FramelessWindowHint`）系统不再提供缩放边框，要自己实现。
见 `ui/resizer.py`。

实现要点：

- **用应用级事件过滤器**，不是在窗口里覆写 `mousePressEvent`。因为工具栏和
  画布几乎铺满窗口，鼠标事件都被子控件吃掉，窗口自己收不到边缘点击。过滤器
  能在事件到达子控件前看到它，从而在边缘处拦截。
- **拦截后必须返回 True**（消费掉），否则拖边缘会同时触发画布平移或工具栏
  拖动。
- **交给系统缩放**（`windowHandle().startSystemResize`），不是自己算几何。
  自己算要处理最小尺寸、屏幕边界、DPI 换算，还要模拟平台的拖动反馈；
  系统做既省事又和平台观感一致。
- **命中区域 6px**。边框只有 1px 用户极难点到；窗口很小时按比例收缩，
  否则整个窗口都是边缘、中间没法操作。
- **最大化时禁用**边缘缩放，与系统窗口管理器一致。

一个 Qt 版本坑：不能用 `event.widget()` 取事件接收者——那是 Qt4 的 API，
Qt5/6 的 `QMouseEvent` 没有这个方法（实测直接 `AttributeError`）。
`eventFilter` 的第一个参数就是接收者，用它。

**判断事件归属必须用 `window()`，不能用 `parentWidget()` 链条。** 弹出式控件
（`QMenu`、下拉框、tooltip）在 Qt 里是**独立的顶层窗口**
（`isWindow() == True`），但它们的 `parentWidget()` 仍指向宿主窗口。用父链判断
会把菜单误认为属于本窗口，于是：

1. 坐标换算 `obj.mapTo(window, ...)` 在弹出窗上用错参考系，算出远离窗口的点；
2. 那点若刚好落在窗口边缘判定区内，过滤器就返回 True 吃掉事件——菜单收不到
   点击，表现为**点 `···` 菜单卡住**（切到别的窗口再切回来才恢复，因为那时
   菜单已关闭）。

用 `widget.window() is self._window` 判断就对了：对弹出窗返回它自己（不等），
对普通子控件返回宿主顶层窗口（相等）。

**光标必须设在鼠标所在的子控件上，不能只设在窗口上。** `QWidget.setCursor()`
设的光标优先于父级，所以窗口上的设置会被子控件自己的光标盖住。画布设了手形
光标（提示可拖动平移），于是**左右边缘看不到缩放光标、以为不能缩放**，而上下
边缘（落在工具栏/状态栏上，它们没设自己的光标）却正常——表现为"只有部分方向
能缩放"这种最容易被当成玄学的问题。

离开边缘时要**恢复该控件原本的光标**，否则画布会一直显示双箭头、丢掉
"可拖动平移"的手形提示。原本的光标在首次接管前记下来。

点「翻译」时若还没识别过，会**自动先补一次 OCR 再翻译**——用户点翻译的意图是
"给我译文"，让他先手动点一次识别是多余的步骤。

「···」按钮是溢出菜单：显示检测框 / 识别文字 / 段落块、复制译文图片到剪贴板。

**叠加层默认关闭**。检测框和置信度标签是排查工具，常驻显示会盖住译文——
用户第一眼想看到的是翻译结果而不是一堆绿框。

### 缩放的三个约束

**占不满的轴无条件居中。** 这是一条硬规则、没有例外：图片缩放后在某方向
小于视图时，该方向必须正好居中——此时它没有平移自由度。注意"占不满就必须
居中"**优先于**锚点不变性：占不满的轴上无所谓锚点，因为无位可移。

**下限 = "至少一个方向贴满视图"**，即 `min(视图宽/图宽, 视图高/图高)`。
到达下限时，先贴满的那个方向**严丝合缝**（gap = 0），另一个方向对称留白。
再往下缩两个方向就都小于视图了（四周全留白），那是要避免的状态。

这是实测微信图片查看器得到的行为：其截图里高度 gap=0、宽度两侧各 58px。
宽图贴左右，高图贴上下。

**余量为 0。** 最初用 24px 余量算 fit/下限，结果图片永远比窗口小一圈、
四周始终有缝，看起来"没贴边"。微信是严丝合缝的，所以不留余量。

下限是**动态**的（取决于图片和视图两者尺寸），方向容易记反：
`min_scale = min(vw/iw, vh/ih)` —— **视图越大下限越高**。所以窗口变大时当前
比例可能低于新下限，必须抬上去；窗口变小时下限下降，当前比例仍合法，
不动它（用户的比例不该被改）。这个方向我第一版写反了。

**溢出轴可拖动**，夹在 `[视图-图片, 0]` 内，防止拖到屏幕外找不回。
放大时以光标为锚点（锚点不变性），但该轴必须处于溢出状态才成立。

**上限 = 1200%**。

#### 三个踩过的坑

**坑一：`relax`（松弛量）让图片被推出视图。** 为了让锚点在"图片从溢出变为不
溢出"的那一档不跳，我给溢出轴的边界加了 ¼ 视图的松弛量。后果：锚点在边角时
（如左上角 `(10,10)`），缩放会把偏移推到 `+31`，而合法上界是 `0`——图片左侧
滑到视图右侧之外，画面右边露出一条黑边，必须拖一下才夹回。全参数扫描
（432 组）里出现 **271 次**，不是偶发。

已彻底移除松弛量。取舍是明确的：严格夹紧会让锚点在溢出边界处漂移（实测最多
54px），但**永远不会让图片滑出视图**。边界处几十像素的锚点偏差几乎察觉不到，
图片滑出去是显眼的视觉错误。

**坑二：`relax` 也不该作用于占不满的轴。** 缩小时某轴一旦变为占不满，宽松
夹紧会让图片停在旧的偏心位置——要再点一下鼠标（触发严格夹紧）才回中。
用户看到的就是"滚轮缩到最小不居中，点一下才生效"。

**坑三：不能用"是否到达下限"决定居中。** 早期只在 `scale <= floor` 时居中，
漏掉了"宽度先于高度变成占不满"的中间档（宽图缩小过程中宽度会先不溢出，
此时还未到下限）。判断条件应该是**每个轴各自是否溢出**，而非全局是否到底。

所以最终 `_clamp_offset` 只做两件事，各自不留余地：

```python
if iw <= vw:  offset.x = 居中          # 占不满 -> 居中，无例外
else:         offset.x = clamp(..., vw-iw, 0)   # 溢出 -> 严格夹紧
```

**回归测试**：`tools/test_zoom.py` 里有一步全参数扫描（6 种视图 × 6 种图片 ×
4 种锚点 × 4 种缩放序列 = **3168 步**），每一步之后都断言这两条规则。
上面三个坑都是这个扫描能抓到的。

## 已知问题

- **OCR 会把紧邻的 CJK 文本并成一个框**。注意这与列分割无关：列分割处理的是
  **多个已经分开的行框**；而这里是 OCR 在检测阶段就把两个词认成了一个框
  （中文词间距太小）。阶段三的列分割能解决前者，后者需要换 OCR 模型或调
  检测阈值。
- **艺术字/LOGO 识别差**（`ANTHROP\C` → `ANTHROPIC`）。装饰字体 OCR 天生吃亏。
- **字体匹配只能对上"族"和"字重"**，区分不了两种不同无衬线（如 Styrene vs
  Helvetica）。要做到后者需要字体识别模型（YuzuMarker.FontDetection 等）。
  当前用微软雅黑 Bold 近似原图的几何无衬线，字重仍偏轻。
- **首次 OCR 推理约 3-6 秒**（模型图优化），之后 2.7-4.3 秒。启动时做了模型预热，
  但没跑真实推理，所以第一次截图仍会吃到这几秒。
- **mss 在 Wayland 下不可用**，pynput 热键在 Wayland 下也不可用（代码会检测并
  提示走托盘菜单）。要支持 Wayland 需换 `xcap` + xdg-desktop-portal。
- **多显示器只抓光标所在的那一个**，且不支持跨屏框选。
